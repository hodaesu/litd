# LITD — Protocole des cinq playtests naïfs

Date : 2026-09-09

## Objet

Valider la compréhension réelle de la verticale PC par cinq personnes qui ne connaissent pas le design de LITD.

Le test mesure ce que le jeu communique seul. Le testeur ne doit pas être guidé vers la « bonne » manière de jouer et l'observateur ne doit pas expliquer les systèmes pendant la session.

## Profil des cinq sessions

- 5 testeurs distincts.
- Priorité à des personnes n'ayant pas suivi le développement de LITD.
- Éviter de tester uniquement avec des joueurs experts de RPG tactiques.
- Les cinq sessions doivent utiliser la même version du build, sauf bug bloquant corrigé entre deux sessions ; dans ce cas, noter précisément le changement de version.

## Consigne donnée au testeur

Dire uniquement :

> « Voici un jeu en cours de développement. J'aimerais que tu joues comme tu le ferais normalement. Je ne vais pas t'expliquer les règles pendant la partie. Dis à voix haute ce que tu crois comprendre, ce que tu essaies de faire et ce qui te paraît étrange. »

Ne pas présenter les neuf piliers, les systèmes, les objectifs de design ni les inspirations avant la session.

## Interdictions pour l'observateur

Pendant le test, ne pas :

- dire où cliquer ;
- nommer un système que le joueur n'a pas identifié ;
- expliquer Peur, Folie, anatomie, blessures, capture ou Rémanence ;
- corriger une décision de jeu ;
- signaler qu'une autre solution existe ;
- défendre une interface ou une mécanique ;
- répondre à « qu'est-ce que je dois faire ? » autrement que par « fais ce qui te semble logique » tant que le build n'est pas réellement bloqué.

Une intervention est autorisée uniquement en cas de bug bloquant, crash, boucle morte ou impossibilité technique de continuer. Toute intervention doit être notée.

## Tâches observées

Le testeur n'a pas besoin de recevoir cette liste. L'observateur la suit en silence.

### A. Sanctuaire

Observer si le joueur :

- comprend qu'il se trouve dans un espace de préparation ;
- identifie son groupe ;
- repère comment lancer une expédition ;
- examine spontanément l'état ou l'équipement d'au moins un Veilleur ;
- comprend ce qui est interactif.

### B. Exploration

Observer si le joueur :

- comprend le déplacement ;
- identifie un objectif ou une direction plausible ;
- remarque les informations contextuelles ;
- distingue choix facultatif et progression obligatoire.

### C. Combat de base

Observer si le joueur comprend sans aide :

- à qui est le tour ;
- quelle unité est active ;
- les cibles possibles ;
- l'effet probable d'une action ;
- l'influence de la position ;
- quand le combat est terminé.

### D. Peur / Folie

Noter :

- le moment où le joueur remarque la jauge ou l'état ;
- les mots qu'il emploie pour l'interpréter ;
- s'il modifie sa décision à cause de cet état ;
- s'il confond ce système avec les PV ou une ressource magique.

### E. Anatomie / blessures

Noter si le joueur :

- remarque qu'un membre ou une fonction est affecté ;
- comprend qu'une blessure a une conséquence autre qu'une perte de PV ;
- change son action, son équipement, sa cible ou son niveau de risque en conséquence.

### F. Capture / coexistence

Observer si le joueur :

- comprend qu'une rencontre ne se résout pas forcément par la mort ;
- découvre une possibilité de capture/coexistence sans explication orale ;
- perçoit le coût, le risque ou la conséquence de cette décision.

### G. Élite / boss

Observer :

- si le joueur réutilise des systèmes appris précédemment ;
- s'il identifie une mécanique spécifique ;
- s'il comprend qu'une décision autre que « infliger plus de dégâts » peut être pertinente ;
- s'il sait pourquoi il a gagné ou perdu.

### H. Retour au Sanctuaire

Observer si le joueur :

- comprend que la session n'est pas terminée immédiatement après le boss ;
- remarque une conséquence persistante ;
- peut expliquer ce qui a changé dans le Sanctuaire, le groupe ou le monde.

## Grille d'observation

Pour chaque événement important, noter :

- horodatage approximatif ;
- écran ou situation ;
- action du joueur ;
- ce qu'il dit croire ;
- résultat réel ;
- hésitation supérieure à 5 secondes : oui/non ;
- erreur récupérable : oui/non ;
- intervention observateur : oui/non ;
- bug : oui/non ;
- sévérité : cosmétique / mineur / majeur / bloquant.

Ne pas remplacer les mots du testeur par le vocabulaire du design. Ses formulations sont une donnée de test.

## Mesures à relever par session

### Compréhension

- Temps avant première action autonome au Sanctuaire.
- Nombre de demandes directes d'aide.
- Nombre d'interventions obligatoires de l'observateur.
- Nombre de mécaniques essentielles comprises avant leur explication post-test.
- Nombre d'erreurs provenant d'une interface ambiguë.

### Progression

- Expédition lancée sans aide : oui/non.
- Premier combat terminé sans aide : oui/non.
- Retour au Sanctuaire atteint : oui/non.
- Session terminée sans blocage : oui/non.

### Décision

- Au moins une décision influencée par la position : oui/non.
- Au moins une décision influencée par Peur/Folie : oui/non.
- Au moins une décision influencée par une blessure/anatomie : oui/non.
- Capture/coexistence comprise : oui/non.
- Conséquence persistante identifiée : oui/non.

### Engagement

- Le joueur souhaite-t-il continuer après la fin du protocole ? oui/non.
- Souhaite-t-il recommencer immédiatement après un échec ? oui/non.
- Cite-t-il spontanément un moment qu'il veut revoir ou mieux comprendre ? oui/non.

## Questionnaire post-session

Poser les questions dans cet ordre, sans donner les réponses entre deux questions.

1. Selon toi, quel était ton objectif principal ?
2. Qu'est-ce qui t'a paru le plus important pendant un combat ?
3. À quoi servaient les positions ?
4. Qu'as-tu compris de la Peur et de la Folie ?
5. Qu'as-tu compris des blessures et de l'anatomie ?
6. As-tu compris qu'une créature pouvait avoir une autre issue que la mort ? Si oui, comment ?
7. Qu'est-ce qui a changé après ton expédition ?
8. À quel moment as-tu été le plus perdu ?
9. Quelle information t'a manqué ?
10. Quelle information t'a semblé inutile ou trop présente ?
11. Quel moment t'a le plus donné envie de continuer ?
12. Quel moment t'a donné envie d'arrêter ?
13. Si tu pouvais changer une seule chose avant de rejouer, laquelle ?
14. Est-ce que tu rejouerais à ce build de ton plein gré ? Pourquoi ?
15. En une phrase, comment décrirais-tu le jeu à quelqu'un qui ne le connaît pas ?

## Entretien de débrief après les questions

Seulement après le questionnaire, l'observateur peut expliquer ce que certains systèmes étaient censés produire et demander :

- « Qu'est-ce qui t'aurait permis de comprendre cela plus tôt ? »
- « Quelle information aurais-tu voulu voir, et où ? »
- « Est-ce que tu avais vu cet élément avant que je le nomme ? »

Ne pas utiliser le débrief pour invalider le ressenti du joueur.

## Gate après cinq sessions

La verticale peut passer à l'itération suivante lorsque :

- [ ] au moins 4 testeurs sur 5 lancent l'expédition sans aide ;
- [ ] au moins 4 sur 5 terminent le premier combat sans intervention ;
- [ ] au moins 4 sur 5 identifient correctement unité active, cible et effet principal d'une action ;
- [ ] au moins 3 sur 5 prennent spontanément une décision influencée par Peur/Folie ;
- [ ] au moins 3 sur 5 comprennent qu'une blessure a un effet fonctionnel ;
- [ ] au moins 3 sur 5 comprennent qu'une rencontre de créature peut avoir une issue non létale ;
- [ ] au moins 4 sur 5 comprennent qu'une conséquence persiste après l'expédition ;
- [ ] au moins 3 sur 5 déclarent vouloir rejouer ou poursuivre ;
- [ ] aucun bug bloquant commun aux sessions ne subsiste ;
- [ ] aucun point d'incompréhension critique n'apparaît chez 3 testeurs ou plus sans correction prévue.

Ces seuils servent de gate de prototype, pas de preuve statistique de qualité commerciale.

## Priorisation des corrections

Après les cinq tests, classer les problèmes dans cet ordre :

1. blocage ou crash ;
2. impossibilité de comprendre l'action suivante ;
3. information critique invisible ou ambiguë ;
4. système central compris à l'envers ;
5. manque de feedback ;
6. friction d'interface ;
7. équilibre ;
8. présentation ;
9. contenu supplémentaire.

Ne pas ajouter du contenu pour masquer un problème de compréhension.

## Rapport final des cinq tests

Créer ensuite un rapport unique contenant :

- version du build ;
- tableau comparatif des cinq sessions ;
- points compris par 5/5, 4/5, 3/5 ou moins ;
- trois principaux blocages ;
- trois moments d'engagement les plus forts ;
- bugs par sévérité ;
- corrections P0/P1/P2 ;
- décision : `RETEST`, `ITERATE`, ou `READY_FOR_NEXT_SLICE`.

Aucune décision `READY_FOR_NEXT_SLICE` ne doit être prise uniquement parce que les cinq joueurs ont réussi à terminer. La compréhension des systèmes signature de LITD compte autant que la progression brute.
